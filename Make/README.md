# Make как единая точка входа

Этот проект демонстрирует, как превратить рутинные действия Python-разработки в воспроизводимый сценарий, управляемый через `Makefile`. В центре решения не отдельные команды, а договорённость о том, что любой запуск, проверка и сборка происходят через локальное окружение проекта и через стабильные `make`-таргеты.

## Идея решения

Ключевая проблема задания связана с тем, что `make` не хранит состояние shell между строками рецепта. Из-за этого подход с `source .venv/bin/activate` ненадёжен: следующая строка уже будет выполняться в новом shell-процессе. Поэтому в проекте используется другой принцип: каждый инструмент вызывается по явному пути из локального окружения, например через `.venv/bin/python` или `.venv/bin/python -m ...`.

Из этого решения следуют несколько важных эффектов:

- зависимости гарантированно устанавливаются именно в проектное окружение;
- запуск приложения и проверок не зависит от того, активировано ли окружение вручную;
- `Makefile` становится единственной понятной точкой входа для всей команды.

## Структура проекта

- `src/demo_app/` — минимальный Python-код для демонстрации запуска, импортов и типизации;
- `tests/` — автоматические тесты;
- `scripts/check_requirements.py` — проверка соответствия импортов и `requirements.txt`;
- `scripts/build_report.py` — сборка небольшого документационного артефакта;
- `requirements.txt` — runtime-зависимости;
- `requirements-dev.txt` — инструменты разработки;
- `Makefile` — единая точка входа.

## Последовательность действий до использования Make

Эта часть нужна для сравнения с автоматизированным вариантом и показывает, что именно теперь берёт на себя `Makefile`.

1. Создать виртуальное окружение внутри проекта.
2. Установить runtime- и dev-зависимости в это окружение.
3. Запускать приложение только через интерпретатор из `.venv`.
4. Отдельно запускать линтер, форматтер, проверку типов и тесты.
5. Следить, чтобы импорты в исходниках не расходились с `requirements.txt`.
6. Следить, чтобы артефакты сборки и локального окружения не попадали в `git status`.

Без `Makefile` эти шаги становятся набором несвязанных команд, и воспроизводимость начинает зависеть от внимательности человека.

## Автоматизация после внедрения Make

Проект поддерживает следующие таргеты:

- `make venv` — создаёт локальное окружение `.venv`;
- `make install` — устанавливает все зависимости в `.venv`;
- `make run` — запускает приложение через интерпретатор проекта;
- `make format` — форматирует код;
- `make lint` — проверяет стиль без изменения файлов;
- `make typecheck` — запускает статическую проверку типов;
- `make check-requirements` — сверяет импорты и `requirements.txt`;
- `make test` — запускает тесты;
- `make docs` — собирает документационный артефакт в `build/assignment-report.md`;
- `make build` — собирает исполняемый `zipapp` в `build/demo_app.pyz`;
- `make check` — объединяет все проверки качества.

Составной таргет `check` показывает, что `Make` описывает связи между действиями. Он не просто повторяет команды, а собирает рабочий конвейер из маленьких переиспользуемых шагов.

## Почему окружение действительно проектное

Гарантия строится на двух решениях:

1. окружение создаётся внутри каталога проекта в `.venv/`;
2. `Makefile` использует переменные `PYTHON`, `PIP`, `RUFF`, `MYPY`, `PYTEST`, указывающие на инструменты именно из `.venv`.

Это поведение реализовано by-design: даже если в системе есть глобально установленные пакеты, `make run`, `make test` и `make check` используют локальный интерпретатор проекта.

## Проверка зависимостей

Скрипт `scripts/check_requirements.py` анализирует Python-файлы в `src/`, извлекает импорты через `ast`, отбрасывает стандартную библиотеку и локальные модули проекта, а затем сравнивает оставшиеся внешние зависимости с `requirements.txt`.

Проверка приближённая, потому что имя импорта и имя пакета не всегда совпадают. Для нескольких популярных случаев в скрипте предусмотрено явное сопоставление, а для остальных используется нормализация имени. Для учебной задачи этого достаточно: цель — не идеальная совместимость со всем PyPI, а автоматизированный контроль воспроизводимости.

## Типы, стиль и тесты

Для статической типизации используется `mypy`, для форматирования и style-check — `ruff`, для тестов — `pytest`. Интерфейс при этом остаётся независимым от инструмента:

- команда проверки типов всегда запускается через `make typecheck`;
- команда style-check всегда запускается через `make lint`;
- форматирование всегда запускается через `make format`.

Это важно, потому что наружный интерфейс проекта должен быть стабильным даже при замене внутреннего инструмента.

## Что проверять при оценке

При проверке решения достаточно выполнить следующие команды из каталога проекта:

```bash
make install
make run
make check
make docs
make build
git status --short
```

Ожидаемый результат:

- приложение запускается через локальное окружение;
- проверки стиля, типов, зависимостей и тесты проходят;
- артефакты сборки и `.venv` не засоряют репозиторий;
- документация и `Makefile` дают полное понимание того, как устроен процесс.
